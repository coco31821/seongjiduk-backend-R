# 포트폴리오 문제 해결·성능 실험 원칙

이 문서는 기능 구현을 포트폴리오의 **문제 정의 → 검증 → 해결 → 재검증** 이야기로
남기기 위한 작업 규칙이다. 새 성능·Redis 작업은 구현 전에 이 문서와 관련 관찰 기록을 읽는다.

## 1. 주장 단위: A → B → C

모든 개선 사례는 아래 세 문장을 증거와 함께 완성한다.

| 단계 | 질문 | 기록해야 할 것 |
| --- | --- | --- |
| A. 문제 | 무엇이 사용자·비용·운영에 영향을 줬나? | 기준선 수치, 재현 조건, 영향 범위 |
| B. 해결 | 원인 가설을 검증하기 위해 무엇을 바꿨나? | 설계, 동시성/장애 처리, 대안 비교 |
| C. 성과 | 같은 조건에서 무엇이 얼마나 달라졌나? | before/after, 변화율, 남은 한계 |

“Redis를 적용했다”는 해결책일 뿐 성과가 아니다. 성과는 같은 조건에서 다시 측정한
응답 시간·처리량·오류·외부 호출량으로만 주장한다.

## 2. 사실·가설·검증 결과를 분리한다

- **사실:** 측정치, 로그, trace, mock 호출 수처럼 재현 가능한 관찰.
- **가설:** 관찰을 설명하는 원인 후보. 확정 사실처럼 쓰지 않는다.
- **검증:** 가설이 맞다면 달라져야 하는 지표와, 반증될 조건을 미리 정한다.
- **결론:** 검증 결과가 뒷받침하는 범위까지만 주장한다.

예: route verification의 “cache stampede” 가설은 AI·Naver mock 호출량이 요청 수에
비례한다는 관찰로 시작한다. Redis distributed single-flight 적용 후 동일 조건에서
AI 195회→1회, Naver 검색 390회→2회가 되면 가설을 지지한다.

## 3. 측정 우선순위

성능 작업은 코드 변경 전에 기준선을 남기고, 변경 후 반드시 같은 조건으로 재측정한다.

| 관점 | 핵심 지표 | 해석 |
| --- | --- | --- |
| 사용자 경험 | p50, p95, p99, 오류율 | 평균만으로 긴 꼬리 지연을 숨기지 않는다. |
| 처리 능력 | completed RPS, dropped iterations | 요청을 실제로 목표 속도로 처리했는지 확인한다. |
| 비용 | AI·외부 API 호출 수, cache hit/miss | 호출 1회가 비용인 외부 의존성을 별도 측정한다. |
| 자원·안정성 | Hikari active/waiting, CPU/메모리, Redis 상태 | 단순히 병목을 다른 계층으로 옮기지 않았는지 확인한다. |
| 분산 불변식 | max in-flight, key별 외부 호출 수, lease 회수 | replica 환경에서도 제한이 유지되는지 확인한다. |

## 4. 해결책을 고르는 기준

대안은 최소 두 개 이상 비교하고, 선택하지 않은 이유를 남긴다.

예: multi-replica cache miss 중복 호출 문제

| 대안 | 장점 | 한계 | 판단 |
| --- | --- | --- | --- |
| JVM local lock | 단순, 빠름 | 인스턴스 간 중복 호출을 막지 못함 | 단일 인스턴스 실험용 |
| Redis `SET NX PX` lock | 단순한 분산 락 | 소유자 검증 해제·lease 연장 직접 구현 필요 | 유효한 대안 |
| Redis lease/heartbeat semaphore | 기존 분산 permit 구조 재사용, 소유자 종료 회수 | Lua·인자 계약 검증 필요 | 현재 선택 |
| replica·DB pool 증설 | 즉시 처리량 완화 | 외부 API/AI 중복 비용은 남음 | 근본 해결 아님 |
| stale-while-revalidate / prewarm | hot cache 지연 감소 | 갱신·첫 miss 정책을 추가 설계해야 함 | 후속 최적화 |

## 5. 실패한 측정도 증거다

기대값과 다른 결과를 숨기지 않는다.

1. 기대한 불변식(예: 동일 contentId의 route AI 1회)을 적는다.
2. 실제 수치가 다르면 성공 지표와 별개로 실패로 판정한다.
3. 로그·metric·코드 계약을 좁혀 원인을 찾는다.
4. 수정 뒤 같은 조건으로 재측정한다.

이번 route single-flight는 첫 측정에서 lock Lua 인자 순서 오류로 fail-open 되어 AI 호출이
18회였다. 로그의 `ConcurrencyLimiter Redis 오류`와 Lua의 lease 인자 계약을 대조해
수정했고, 재측정에서 AI 1회·Naver 검색 2회로 검증했다.
